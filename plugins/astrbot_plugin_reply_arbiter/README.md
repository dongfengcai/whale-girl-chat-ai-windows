# reply_arbiter — 多人 @ 时的回应仲裁

对应**需求 7**：

> 如果群聊同时被多人 @，则根据上下文优先回应之前一直在聊的，把之前的内容接下去，
> 否则回应最先 @ 的。

## 问题场景

群里有 A、B、C 三个人，短时间内先后 @ 了机器人：

```
A: @bot 这个怎么弄
B: @bot 在吗
C: @bot 帮我看看这个报错
```

如果三条都独立触发，机器人会**回三次**，既刷屏又割裂 —— 明显不像真人。
真人会**合并成一次回应**，并且优先接住正在进行的对话。

## 仲裁规则

```
收到一次 @ 事件
      │
      ▼
① 去重：同一发送者在窗口期内的重复 @ 只算一次
      │
      ▼
② 判定优先级：
      │
      ├─ 该发送者在「近期上下文」里出现过？
      │        │
      │        ├─ 是 → 高优先级（接续之前的对话）
      │        │
      │        └─ 否 → 低优先级
      │
      ▼
③ 决策：
      ├─ 只被 1 人 @        → 直接回应
      ├─ 被多人 @，有人在高优先级 → 回应**最近**出现过的那个高优先级用户
      └─ 被多人 @，都在低优先级   → 回应**最早** @ 的那个
```

### 「近期上下文」怎么判定

维护一个**每群的发言者时间线**，记录最近 `context_window` 秒内哪些用户发过言
（不只是 @ 机器人的消息，普通发言也算 —— 因为"一直在聊"通常指的是群里的活跃对话）。

判定为"之前一直在聊"的条件（任一满足）：

1. 该用户在最近 `context_window` 秒内发过言 **且** 机器人回应过他
2. 该用户是机器人**上一条回复所针对的人**（直接接续）

条件 1 保证"接住进行中的对话"，条件 2 保证"追问能被接住"。

### 合并窗口

收到第一个 @ 后，**等待 `merge_window` 毫秒**再处理，把窗口内其它 @ 一起考虑：

```
t=0ms    A @bot          → 启动合并窗口（默认 2000ms）
t=800ms  B @bot          → 并入本次
t=1500ms C @bot          → 并入本次
t=2000ms 窗口关闭        → 仲裁，只回复一次
```

**只回复一次**，但回复时能"看到"三个人的问题，可以一并作答。
这比回三条更像真人。

## 决策示例

| 场景 | 近期上下文 | 回应对象 |
|---|---|---|
| A 单独 @ | 无 | A |
| A、B 同时 @，A 刚聊过 | A 在上下文中 | **A**（接续对话） |
| A、B 同时 @，都刚聊过 | A 更近 | **A**（最近的那个） |
| A、B 同时 @，都没聊过 | 无 | **A**（最早 @ 的） |
| A、B 同时 @，B 刚聊过 | B 在上下文中 | **B**（即使是后 @ 的） |

注意最后一行 —— 这正是需求里说的"优先回应之前一直在聊的"，
**哪怕对方是后 @ 的也要优先接住**。

## 配置项

| 项 | 默认 | 说明 |
|---|---|---|
| `enabled` | `true` | 总开关 |
| `merge_window_ms` | `2000` | 合并窗口。太短会漏掉后续 @，太长显得迟钝 |
| `context_window_seconds` | `300` | 判定"一直在聊"的回看时长（5 分钟） |
| `require_mention_in_group` | `true` | 群聊必须 @（需求 6） |
| `require_mention_in_private` | `false` | 私聊免 @（需求 6） |
| `bypass_admin` | `true` | 管理员 @ 立即响应，不进合并窗口 |

### 关于 `merge_window_ms` 的取舍

| 值 | 效果 |
|---|---|
| `0` | 无合并，谁先 @ 回谁（回到无仲裁状态） |
| `2000`（默认） | 平衡：能收住连发的 @，延迟可接受 |
| `5000` | 收得更全，但用户会感觉"怎么不回我" |

在活跃群里 `2000` 比较合适。冷清群可以调到 `1000`，让响应更及时。

## 需求 6：@ 规则

| 场景 | 是否回应 |
|---|---|
| 群聊被 @ | ✅ 回应 |
| 群聊未被 @ | ❌ 完全不理（即使提到关键词） |
| 私聊 | ✅ 回应（不需要 @） |
| 群聊被 @ 但是语音/视频 | ❌ 由 `media_pacer` 跳过 |

群聊不 @ 就不理，这是"被动聊天"的核心 —— 机器人不会插嘴。

## 边界情况

| 情况 | 行为 |
|---|---|
| 合并窗口内同一个人 @ 三次 | 去重，只算一次 |
| 窗口内 @ 后又撤回了消息 | 尽力处理；撤回事件拿不到原文时按"已收到"处理 |
| 高优先级用户 @ 了但内容为空（纯 @） | 仍回应（"在吗"这类也算） |
| 机器人自己的消息 | 忽略，不自我触发 |
| 窗口期内又来了新的 @ | **不延长窗口**（避免活跃群里无限等待），进入下一轮仲裁 |
| AstrBot 重启 | 上下文时间线丢失（内存态），退化为"回应最早 @"，不影响可用性 |

最后一条要说明：时间线**存在内存里**，不落盘。因为它是短期上下文（5 分钟窗口），
重启后重建的代价只是短暂失去"接续"能力，不值得为它增加写盘开销和复杂度。

## 日志

```

[reply_arbiter] 群 123456 并入 @ user:B

[reply_arbiter] 群 123456 仲裁：候选 [A, B] → 回应 A（均不在上下文，取最早 @）
```
