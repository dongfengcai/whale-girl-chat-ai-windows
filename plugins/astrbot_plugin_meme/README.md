# meme — 表情包

让模型按语境发表情包，并支持从群聊自动收集表情。

## 两种"表情"分开处理

需求里的"发表情"其实是两件事，实现方式完全不同：

| 类型 | 例子 | 谁负责 | 成本 |
|---|---|---|---|
| **Emoji 字符** | 😂 🐳 🤔 | **人设**（见下节） | 零代码、零成本 |
| **表情包图片** | 一张熊猫头 | **本插件** | 需要图库 |

**Emoji 不需要插件** —— 那只是模型输出的文本，在人设里鼓励它用就行。
本插件只负责图片。

## 模型怎么"要"一张图

模型没法直接发图（它只能输出文字）。所以流程是：

```
模型输出：（小明·群主）哈哈哈 [表情:大笑]
                        │
                        ▼  插件在 on_decorating_result 钩子里解析
实际发送：（小明·群主）哈哈哈
          + 一张「大笑」类的表情包图片
```

标记会被**从文字里摘掉**，你看到的回复是干净的。

### 为什么不用 function calling

`@filter.llm_tool` 需要模型稳定支持函数调用，接入行为我无法确定。而**标记方案只依赖文本生成** —— 任何模型都能用，不受 function calling 支持情况影响。

### 为什么标签是固定词汇表

```
开心 大笑 害羞 无语 疑问 震惊 生气 委屈
赞同 拒绝 累了 吃饭 哭泣 得意 摸鱼 睡觉
```

模型只从这 16 个里挑一个，**不用描述图片**。让它自由描述（"一张熊猫捂脸笑的图"）几乎必然匹配不到实际库存，固定词汇表的命中率是可控的。

## 完整使用流程

**默认全自动，你什么都不用做：**

```
群里有人发表情
      ↓  插件自动收集（去重、限大小）
   待筛选池
      ↓  自动排队 + 视觉模型打标签（默认开）
    图库          ← 到此模型就能用了
```

打标签是**后台串行**做的，每张间隔 3 秒，不会拖慢聊天，也不会打爆 2GB 内存。

### 何时需要你介入

| 情况 | 处理 |
|---|---|
| 图库为空时 | 模型不会尝试发表情（设计如此，避免挑到空标签） |
| 模型判断不出情绪 | 图**留在池子里**，用 `/表情 池` 看，手动打标签 |
| 每日上限用完 | 剩余图留在池子，第二天继续，或手动打 |
| 想调整标签 | `/表情 标签 <编号> <标签>` 手动指定 |

## 自动打标签

用当前对话模型（`deepseek-flash`）判断每张图的情绪。

### 成本

一张图约 **765 token**（含图片编码）。按 `deepseek-flash` 非高峰价（输入 $0.15/百万）：

| 数量 | 成本 |
|---|---|
| 50 张/天（默认上限） | 约 ¥0.04/天 |
| 300 张（满库） | 约 ¥0.25 一次性 |

**默认每日上限 50 张**，防止被刷图刷爆账单。超过上限的图留在池子里。

### ⚠️ 依赖视觉能力

| 模型 | Vision |
|---|---|
| `deepseek-flash` | ✅ 支持 |
| `deepseek-v4-pro` | ❌ **不支持** |

**换模型会让自动打标签失效**（图会一直留在池子里）。

### 判断不出情绪时

模型看不出来会返回空标签，此时按 `auto_tag_unclear` 处理：

| 值 | 行为 |
|---|---|
| `keep`（默认） | 留在池子里等你手动处理 |
| `discard` | 直接删掉 |

**默认 `keep`** —— 判断不出不代表没用，可能只是模型理解不了这个梗。

### 为什么串行 + 间隔

2GB 内存 + 限速 API，**并发调视觉模型很容易把内存打爆或触发限流**。串行慢一点但稳。

## 手动管理（仍然可用）

管理员（`admin_qq` 或 AstrBot 管理员）私聊机器人：

| 指令 | 作用 |
|---|---|
| `/表情 状态` | 图库/池子/标签数 + 自动打标签进度 |
| `/表情 池` | 列出待筛选的图（带编号） |
| `/表情 标签 <编号> <标签>` | 手动入库 |
| `/表情 丢弃 <编号>` | 从池子里删掉 |
| `/表情 标签表` | 看每个标签各有多少张 |

**手动和自动可以混用** —— 自动打错的可以用 `/表情 标签` 覆盖，判断不出的可以手动补。

## 收集机制

```
群里有人发表情  →  待筛选池  →  自动打标签  →  图库（模型可用）
```

### 怎么判断是表情包

优先看 OneBot 原始消息里的 `sub_type`：NapCat 对表情包标 `"1"`，普通图片标 `"0"`。

**拿不到 `sub_type` 时宽松放行** —— 宁可多收几张让你筛选，也不要漏掉。反正都要人工打标签，多收的成本只是池子占位。

### 去重

用**图片内容的 SHA256** 去重，库和池子里已有的都不再收。同一张图被反复转发不会重复入库。

## ⚠️ 流式输出的坑（重要，建议关掉流式）

AstrBot 的**流式输出**会干扰本插件。日志里可能出现：

```
[WARN] [result_decorate.stage:169]: Plugins that depend on the pre-send event hook
may not work correctly when streaming output is enabled.
```

### 为什么

看 AstrBot 源码 `result_decorate/stage.py`：

```python
# L134  流式时内容已边生成边发出，消息链被清空
if result.result_content_type == ResultContentType.STREAMING_RESULT:
    event.clear_result()

# L158  钩子仍会调用，只是会打那条警告
for handler in handlers:
    if is_stream:
        logger.warning("Plugins that depend on the pre-send event hook ...")
    await handler.handler(event)
```

所以那条 WARN 是**提醒，不是崩溃** —— 钩子确实执行了。但后果是真实的：

| | 非流式 | 流式 |
|---|---|---|
| 能否剥掉标记 | ✅ | ❌ 文本早发出去了 |
| 能否在回复里插图 | ✅ | ❌ 链子已不用 |

### 本插件的处理：两条路径都兜住

```
非流式：剥掉标记 → 把图插在文字后面（一条消息，最干净）
流式：  剥不掉 → 发一张独立图片作为补偿
```

流式下用户会看到 `[表情:开心]` **外露在文本里**，然后才收到图片。这是流式的固有限制，不是插件的 bug。

### 推荐操作：关掉流式输出

**面板 → 模型提供商 / 提供商设置 → 关闭「流式输出」（streaming）**

关掉后一切走非流式路径：标记被干净摘掉，图片和文字在同一条消息里。

代价是回复不再逐字蹦出 —— 但**对聊天机器人来说这反而更像真人**（真人不会一个字一个字往外蹦）。

### 为什么用独立消息而不是硬改链子

流式下改消息链**来不及** —— 内容已经发出去了。独立消息在任何输出模式下都成立，所以它是可靠的兜底路径。

## 配置项

| 项 | 默认 | 说明 |
|---|---|---|
| `enabled` | `true` | 总开关 |
| `send_enabled` | `true` | 允许模型发表情包 |
| `collect_enabled` | `true` | 自动收集群里的表情 |
| `collect_groups` | `[]` | 收集来源群号，留空 = 所有群 |
| **`auto_tag`** | **`true`** | **自动打标签（省去手动操作）** |
| `auto_tag_provider` | 空 | 打标签用的提供商 ID，留空 = 当前对话模型 |
| `auto_tag_daily_limit` | `50` | 每日自动打标签上限（控成本） |
| `auto_tag_interval_seconds` | `3` | 每张之间的间隔 |
| `auto_tag_unclear` | `keep` | 判断不出时：`keep` 留池 / `discard` 丢弃 |
| `library_limit` | `300` | **图库上限** |
| `pool_limit` | `60` | 待筛选池上限 |
| `max_file_mb` | `1.0` | 单张大小上限 |
| `send_probability` | `0.7` | 即使模型要发，也只有这个概率真发 |
| `require_text` | `true` | 发图时必须带文字 |
| `admin_qq` | 已预填 | 管理指令的使用者 |

### 为什么有 `send_probability`

模型有时会**每条都想发表情**。0.7 保留随机性，避免看起来像"每句都配一张图"的机器人。想让它每次都发就设 `1.0`。

| 指令 | 作用 |
|---|---|

| `/表情 池` | 列出待筛选的图（带编号） |
| `/表情 标签 <编号> <标签>` | **入库**：给某张图打标签 |
| `/表情 丢弃 <编号>` | 从池子里删掉 |

### 典型流程

```
群友发了几张表情包
        ↓
你私聊机器人：/表情 池
        待筛选池：
        1. a3f2b1c9.gif
        2. 7d4e8f02.jpg
        ↓
你：/表情 标签 1 大笑
        已入库 [大笑]，图库 1/300 张。
        ↓
之后模型在合适的语境就会用上它
```

## 数据位置

```
data/plugin_data/astrbot_plugin_meme/
├── index.json      标签 → 图片路径 的映射，以及待筛选池
├── library/        已入库的图（模型可用）
└── pool/           待筛选的图
```

放在 `plugin_data/` 而不是插件目录 —— **更新或重装插件不会丢图库**。

## 日志

```
[meme] 启动：图库 42/300 张，待筛选 5 张，标签 16 个（收集已开）
[meme] 收集到表情，待筛选池 6 张（打标签后才能被模型使用）
[meme] 发出表情 [大笑] -> a3f2b1c9.gif
[meme] 模型用了无效标签 ['狗头']，已忽略
```

## 边界情况

| 情况 | 行为 |
|---|---|
| 模型用了不存在的标签 | 摘掉标记、不打图、记日志，**不影响正常回复** |
| 模型写了 `[表情：开心]`（全角冒号） | 能匹配 |
| 模型写了两个标记 | 只取第一个有效的，最多发一张 |
| 图库为空 | 完全不给模型提示，它不会尝试发表情 |
| `require_text` 开着但文字为空 | 不配图（避免只发一张图没有文字） |
| 图库满了 | 打标签时拒绝并提示，明确告诉你上限 |
| 单张图超过大小上限 | 不收 |
| 图片下载失败 | 静默跳过，记 debug 日志 |
| 非 OneBot 平台 | `sub_type` 拿不到，宽松收集 |

## 配套人设

Emoji 字符靠人设鼓励。在【怎么说话】里加一句：

```
可以用 emoji 表达情绪，比如 😂 🐳 🤔 😴，但别每条都用。
```

表情包的标记由插件注入提示词告诉模型，**不需要在人设里写**。
