# balance_guard — 余额红线 + 群额度守护

对应**需求 1**（余额红线）以及追加需求（每群每日 token 上限）。

## 两道防线

```
                    ┌─────────────────────────────┐
   每条消息 ───────▶│ ① 全局熔断？（余额 ≤ 红线） │
                    └──────────┬──────────────────┘
                               │ 否
                               ▼
                    ┌─────────────────────────────┐
                    │ ② 本群额度用尽？（每日 token）│
                    └──────────┬──────────────────┘
                               │ 否
                               ▼
                          正常送 LLM
```

两道防线互相独立：**某个群刷爆了只停那个群，其它群照常**；余额触线则全局停。

---

## ① 余额红线

```
每 N 分钟轮询 GET https://api.deepseek.com/user/balance
        │
        ├─ 余额 > 红线            → 正常
        └─ 余额 ≤ 红线            → 告警 + 熔断（全局停止回复）
```

采用**方案 B**：熔断时插件不退出、容器不停止，只是拒绝把消息送进 LLM。
充值后发一条指令即可恢复，或等下一次轮询自动发现余额回升。

### 为什么按 `total_balance` 而不是充值余额

DeepSeek 扣费**优先消耗赠金**。按 `topped_up_balance` 判断的话，赠金烧完时
充值余额还是满的、红线不触发，但实际已经无法调用 API。按总额才符合
"钱花完了就停"的真实语义。

### 恢复流程

1. 到 https://platform.deepseek.com/top_up 充值
2. 管理员私聊机器人发送 `余额恢复`
3. 插件立即重新查询，高于红线则解除熔断

也可以等下一次轮询自动恢复 —— 熔断状态下**仍会继续轮询**，余额回升即自动解除。

## ② 每群每日 token 上限

### 用量从哪来 —— 真实统计，不是估算

用量直接查 AstrBot 的 **`provider_stats` 表**（`astrbot/core/db/po.py::ProviderStat`），
由框架在每次回复后写入，字段包括：

| 字段 | 含义 |
|---|---|
| `umo` | 会话标识（群/私聊），按它分组 |
| `token_input_cached` | 命中缓存的输入 token |
| `token_input_other` | 未命中缓存的输入 token |
| `token_output` | 输出 token |
| `created_at` | 时间戳 |

口径：`token_input_cached + token_input_other + token_output`。
**这包含了人设、记忆、历史上下文**，不只是用户那句话 —— 所以能真实反映花费。

> 这点很重要：如果只统计用户消息的字数，会严重低估实际消耗，
> 因为每轮请求都要带上完整上下文。

### 计费周期

默认**每天零点**（本地时区）重置，可用 `group_limit_reset_hour` 改成任意整点。

### 达上限后

- 该群消息被拦在 LLM 之前，**不做任何回复**
- 发出一次提示（内容可配置，留空则静默）
- **其它群完全不受影响**

### 缓存

用量查询结果缓存 **30 秒**。每条消息都查库没有意义，30 秒粒度对"每日额度"
这种量级完全够用，也避免了数据库压力。

### 管理员重置

管理员私聊机器人：

```
额度恢复 <群号>
```

实现方式是记下**当前窗口的累计总量**作为扣减基线（绝对值，不是增量 ——
否则连续重置会重复累加、第二次就失效）。插件**不会去改 `provider_stats` 表**，
那是框架的统计表。

## 配置项

### 余额部分

| 项 | 默认 | 说明 |
|---|---|---|
| `api_key` | 已预填 | DeepSeek API key，**可在面板修改**。留空则从 AstrBot 提供商配置读取 |
| `red_line` | `5.0` | 红线金额 |
| `currency` | `CNY` | 币种，`CNY` / `USD` |
| `balance_field` | `total_balance` | 判定字段（含赠金） |
| `check_interval_minutes` | `10` | 轮询间隔 |
| `notify_once` | `true` | 触线只告警一次 |
| `failure_threshold` | `3` | 连续查询失败几次才告警 |
| `blocked_reply` | 见 schema | 熔断时的提示语，留空 = 完全静默 |

### 群额度部分

| 项 | 默认 | 说明 |
|---|---|---|
| `group_daily_token_limit` | `200000` | 每群每日 token 上限，**0 = 不限制** |
| `group_limit_reset_hour` | `0` | 额度重置时间（0-23 点，本地时区） |
| `group_limit_notify` | 见 schema | 额度用尽提示语，可用 `{limit}` 占位。留空 = 静默 |
| `group_limit_command` | `额度恢复` | 管理员重置指令 |

### 通用

| 项 | 默认 | 说明 |
|---|---|---|
| `enabled` | `true` | 总开关（关掉＝两道防线都停） |
| `admin_qq` | 已预填 | 接收告警 + 执行恢复指令 |
| `notify_targets` | 空 | 额外告警接收者，`group:群号` / `private:QQ号` |
| `resume_command` | `余额恢复` | 管理员余额恢复指令 |

## 上限该设多少

按 DeepSeek 非高峰价（`deepseek-flash`，输入 $0.15 / 输出 $0.6 每百万 token）估算：

| 每群每日上限 | 大致对应 | 满额月成本（约） |
|---|---|---|
| 100,000 | 约 30-60 轮对话 | ~$0.5 |
| 200,000（默认） | 约 60-120 轮 | ~$1 |
| 1,000,000 | 约 300-600 轮 | ~$5 |

实际轮数取决于人设长度和历史上下文大小 —— **上下文越长，每轮消耗越高**。
如果人设写得很长或开了长期记忆，同样的上限能支撑的轮数会明显减少。

建议先按默认 `200000` 跑几天，看日志里的实际用量再调整。

## 边界情况

| 情况 | 行为 |
|---|---|
| 余额查询网络失败 | **不熔断**，沿用上次值；连续失败达阈值才告警 |
| 首次启动还没查到余额 | 不熔断（避免误伤） |
| `is_available=false` | 立即熔断，视同触线 |
| **用量数据库查询失败** | **不封群**，沿用上次值。宁可漏封也不能因一次查询失败误伤 |
| 私聊消息 | 不计入群额度，也不受群额度限制 |
| 插件重载 | 群额度缓存清空、重新查库；扣减基线存 KV，不受影响 |
| 跨计费周期 | 累计值重新变小，`max(0, ...)` 压回 0，不会出现负额度 |

**核心原则：宁可漏报也不误杀。** 网络抖动或查询失败导致的误封比漏一次告警烦人得多。
